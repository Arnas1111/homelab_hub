Automation guide

One rule per line. No canvas, scripts, or programming setup required.

StartCommandsValuesExamplesBehaviorLimits

Start

Open Zigbee → Automations, choose New automation, enter a name and rule, then select Check rule and Save. Use the device reference in the in-app guide for exact device names, reported properties, writable actions, enum options, and number ranges. A device ID may be used instead of a name if names are duplicated.

Every path begins with when or at and must contain at least one do. Start another path with another when or at. Paths run independently. Blank lines and lines starting with # are ignored. Spaces around operators and = are optional.

Save the automation timezone in Settings before using a clock, window, or solar condition. Solar instructions also require solar times enabled and a location in Settings.

Commands

SyntaxMeaning
when "Device".property == valueStarts when that device sends a matching report. The property must be a reported boolean, enum, or number.
at 18:00
at sunrise
at sunset+15m		Starts once per local day at that clock or solar time. Solar offsets may be from −180m to +180m.
if "Device".property != valueContinues only if the latest reported state matches now. A later if is an AND condition. If the device is unavailable, the path stops.
during 18:00..05:30Continues within a local time window. A window crossing midnight is one continuous interval. The start is included; the end is excluded.
after 18:00
before sunrise-20m		Continues when the current local time is after or before the boundary. Clock boundaries cannot have offsets.
wait 5s
wait 2m
wait 1h		Pauses this path for 1 to 86400 seconds. A repeated matching trigger restarts the same wait.
do "Device".power = onSends a supported action to a device. Use the writable property name without set_, for example power, brightness, or color_temp.

The first instruction may also be if for compatibility; later if and and both mean a state check. Use separate paths for OR behavior.

Values and comparisons

Put device names in double quotes: "Flur". A device ID can be used the same way. Property names are unquoted and must match the device reference. Text enum values are case sensitive and can be quoted: "double".

TypeAccepted valuesComparisons
Booleantrue/false, on/off, 1/0==, !=
NumberDecimal numbers in the device's supported range==, !=, <, <=, >, >=
EnumOne of the exact options shown in the device reference==, !=

= is accepted as an alias for == in a trigger or state check. Actions always use =. White light and brightness are separate capabilities; use brightness for full brightness when exposed by the lamp.

Examples

Motion light, 18:00–05:30

when "Bewegungsmelder Flur".occupancy == true
during 18:00..05:30
do "Flur".power = on

when "Bewegungsmelder Flur".occupancy == false
during 18:00..05:30
wait 5s
if "Bewegungsmelder Flur".occupancy == false
do "Flur".power = off

The final check avoids turning the light off if motion returned during the wait. If the sensor stops reporting or the last clear report arrives after 05:30, this rule does not guarantee a switch-off; add a separate 05:30 cutoff path if you want one.

Button action

when "Hall button".action == "double"
do "Flur".power = on

Temperature threshold

when "Outside sensor".temperature < 5
if "Window sensor".contact == false
do "Heater switch".power = on

Sunset and bedtime

at sunset+15m
do "Garden light".power = on

at 23:00
do "Garden light".power = off

Brightness

when "Hall button".action == "single"
do "Flur".power = on
do "Flur".brightness = 100

Replace the example names and properties with values from your own device reference. The example's 100 must be within that lamp's reported brightness range.

What happens when a rule runs

when runs on fresh device reports; it is not a continuous loop. A later if reads the Hub's latest reported state at that moment. A do sends a command, but the next if may still see the old state until the device reports back. Use wait and a later if when you need a fresh check.

Time conditions are checked when reached. A during before a wait allows the delayed action to finish after the window closes. Delayed paths persist across Hub restarts, and failed delayed actions are retried. Disabling or deleting a rule does not cancel delays already scheduled by it. A new report on the same trigger path restarts its matching wait.

The Hub executes every matching path; separate automations can both control the same device. Use the automation status card to see whether a rule is enabled and its most recent result.

Limits and safety

Rules can use up to 50 internal steps and a 24-hour wait. Only discovered Zigbee devices and actions exposed by them can be used. This language supports event triggers, current-state checks, time conditions, waits, and actions. It does not run JavaScript, loops, arbitrary calculations, network calls, or unrestricted programs. Older canvas rules remain active; if one cannot be converted safely, its original data is shown in the editor until you replace it with text.
